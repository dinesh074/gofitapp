GOFIT.TODAY — MASTER ARCHITECTURE & DEVELOPMENT BRIEF

Build gofit.today as an Indian-first Food Intelligence + Nutrition + Training platform, not a generic calorie tracker.

CORE PRINCIPLE
AI understands.
Database knows.
Deterministic code calculates.
Rules engine validates.
Combination engine optimizes.
AI explains.

Everything must operate on one canonical Food Intelligence Graph. Do not build separate nutrition databases for scanner, logging, recipes, planning, or coaching.

CURRENT STACK
- Frontend: existing gofit.today frontend; preserve existing UI unless required.
- Backend: Render Free for MVP.
- Database: Supabase PostgreSQL + Auth + Storage; use pgvector where useful.
- AI: Gemini API initially.
  - Gemini 2.5 Flash-Lite for cheap/simple operations.
  - Gemini 2.5 Flash for harder reasoning and image/multimodal operations.
  - Keep AI provider replaceable so Qwen/OpenAI/other providers can be added later.
- Do not self-host GPUs during MVP unless real usage proves it necessary.

AI PROVIDER ABSTRACTION
Create an AIProvider interface with implementations such as:
- GeminiProvider
- FutureQwenProvider
- FutureOpenAIProvider

Do not scatter Gemini-specific calls throughout the application.

FOOD INTELLIGENCE GRAPH
Core entity: FoodEntity.

Relationships:
- aliases
- translations
- nutrients
- portions
- recipes
- recipe variants
- preparation methods
- dietary rules
- allergens
- regional classifications
- cuisine
- substitutions
- images
- source/provenance
- meal combinations
- tags

Food entity types:
ingredient, dish, recipe, breakfast, snack, dessert, beverage, restaurant_food, packaged_food, meal_combination.

Model canonical food + variant + preparation + portion rather than unrelated duplicate foods.

Examples:
Paneer -> raw, grilled, tikka, butter masala, palak paneer, bhurji.
Rice -> steamed, fried rice, lemon rice, curd rice, pulao, biryani.
Chicken -> grilled, boiled, tandoori, curry, butter chicken, fried, biryani.

NUTRITION MODEL
Support:
- kcal, kJ
- protein, carbohydrate, available carbohydrate, starch, total/free sugar, fibre
- total fat, saturated, MUFA, PUFA, trans fat, omega-3, omega-6, cholesterol
- calcium, iron, magnesium, phosphorus, potassium, sodium, zinc, copper, manganese, selenium, iodine, chromium, molybdenum
- vitamins A, B1, B2, B3, B5, B6, B7, B9, B12, C, D, E, K
- carotenoids, beta-carotene, lycopene, lutein, zeaxanthin
- amino acids where reliable data exists: leucine, isoleucine, valine, lysine, methionine, phenylalanine, threonine, tryptophan, histidine.

NEVER invent nutrient values.
Every nutrient value needs:
source_id, source_record_id, source_version, value_status, confidence.

value_status:
measured, calculated, estimated, trace, missing.

Unknown != zero. Use NULL + missing status where data is unavailable.

DATA PROVENANCE
Create a data_sources registry with:
source_id, source_name, source_type, version, publisher, url, license_status, allowed_use, notes.

Do not scrape/copy restricted nutrition databases into production without permission. Use authoritative Indian food composition resources where legally permitted and preserve provenance/version information.

SCALE STRATEGY
Do not manually create 1,000,000 foods.

Target:
- Phase 1: ~20,000 high-quality canonical records.
- Phase 2: 50,000–100,000 canonical + variants.
- Phase 3: 100,000–300,000 food/recipe/preparation/portion variants.
- Phase 4: 1,000,000+ validated meal combinations.

The 1M combinations are generated from foods + recipes + portions + preparations + meal templates + dietary rules + nutrition constraints + regional preferences + user preferences.

The dynamic search space can be much larger than 1M.

COMBINATION ENGINE
Build deterministic:
generateMeal()
findMeals()
rankMeals()
findSubstitutions()
findMealsForNutritionGap()
generateDailyPlan()
generateWeeklyPlan()

Inputs:
calories, protein, carbs, fat, fibre, micronutrient gaps, meal type, diet, allergens, region, cuisine, goal, training context, available ingredients, budget, cooking time, meal size, preferences.

Pipeline:
1. Filter candidates.
2. Apply dietary rules.
3. Apply allergens.
4. Apply exclusions.
5. Apply calorie constraints.
6. Apply macro constraints.
7. Score micronutrients.
8. Apply meal-type constraints.
9. Apply regional/cuisine preferences.
10. Apply user preferences.
11. Apply variety/diversity.
12. Rank.
13. Return top candidates.

LLM must not perform final nutrition arithmetic.

JAIN
Implement as a configurable ruleset, not food.jain=true. Support configurable exclusions/preparation rules because practices can vary. Validate recipes against the selected profile.

SATTVIC
Implement as a configurable ruleset with strict/custom profiles. Do not claim one universal definition.

ALLERGENS
At minimum:
milk, lactose, egg, peanut, tree nuts, soy, wheat/gluten, sesame, fish, shellfish.
States: contains, may_contain, free_from, unknown.
Never infer allergy safety from an LLM.

PORTIONS
Support grams/ml and Indian household units:
katori, bowl, cup, glass, plate, ladle, teaspoon, tablespoon, roti, paratha, dosa, idli, piece, slice, plus food-specific portions such as 1 idli, 2 idli, 1 dosa, 1 roti, 2 roti, 1 katori dal, 1 bowl rice.
Map portions to weight where reliable and store source/confidence.

RAW VS COOKED
Explicitly model raw, cooked, boiled, steamed, fried, deep-fried, air-fried, grilled, roasted, pressure-cooked.
Use cooking-yield factors. Do not treat raw and cooked values as interchangeable.

RECIPE ENGINE
Recipe:
- ingredients
- quantities
- preparation
- cooking method
- steps
- servings
- yield
- raw/cooked state.

Calculate recipe nutrition from ingredients where possible.
Support per 100g, per serving, bowl and custom portion.
Preserve calculation provenance.

HOMEMADE VS RESTAURANT
Model:
homemade, restaurant, street_food, packaged.
Allow materially different nutritional profiles.
When uncertain, return a range/confidence instead of false precision.

FOOD SCANNER
IMAGE -> Gemini Vision -> candidate foods -> portion estimate -> preparation estimate -> confidence -> Food Intelligence Graph -> exact matching -> NutritionEngine.

AI returns structured candidates, not authoritative calories.
Example:
{
  "items": [
    {
      "candidate_food": "masala dosa",
      "confidence": 0.89,
      "portion": {"value": 1, "unit": "medium_dosa"}
    }
  ]
}

Confidence:
- high: automatic result
- medium: ask for confirmation
- low: ask user to choose/clarify.

MANUAL LOGGING
Example:
"2 rotis + dal + curd"
-> parser
-> 2 x roti, 1 x dal, 1 x curd
-> FoodEntity resolution
-> portion resolver
-> NutritionEngine.

VOICE LOGGING
Speech-to-text -> parser -> FoodEntity -> portion resolver -> NutritionEngine.

SUBSTITUTION ENGINE
Support food, ingredient, protein, dairy and carb substitutions.
Rank by protein, calories, fat, carbs, micronutrients, diet, allergens, category/taste, availability.

MICRONUTRIENT GAP ENGINE
Calculate daily and weekly intake and identify relative gaps.
Use wording like "Your logged intake is relatively low in..." rather than diagnosing deficiencies.
Use the combination engine to suggest foods/meals that help close gaps.

FIX MY DAY
Given consumed calories/nutrients and targets:
1. Calculate remaining nutrition.
2. Apply dietary rules.
3. Apply preferences.
4. Search combinations.
5. Rank.
6. Explain.
Example: 1200 consumed, 2000 target, 55g protein remaining -> find 3 suitable options.

DAILY PLANNER
Consider calories, macros, micronutrients, diet, allergens, preferences, cuisine, region, training, ingredients, budget, cooking time.
Slots: breakfast, lunch, snack, dinner, optional pre/post-workout.

WEEKLY PLANNER
Optimize the week rather than each meal independently.
Consider weekly calories, protein consistency, micronutrient diversity, variety, ingredient reuse, budget and cooking effort.
Generate grocery list.

TRAINING-AWARE NUTRITION
Eventually support running, cycling, strength, walking and other exercise.
Use training context for pre-workout, post-workout, recovery, higher-carb training days and rest days.
Do not make medical claims.

REGIONAL INDIAN FOOD MODEL
Structure:
India -> state -> region -> cuisine -> dish -> recipe -> preparation -> portion.
Support North, South, West, East, Northeast, Central and Pan-Indian, eventually state/city/cuisine detail.

LANGUAGE / ALIASES
Support English, Hindi, Hinglish, regional-language names, transliterations and common misspellings.
Examples: roti/chapati/phulka; sabzi/sabji; curd/dahi.
Aliases map to canonical FoodEntity.
Use pgvector where useful.

FOOD SEARCH
Support exact, fuzzy, alias, semantic, regional, dietary and nutrient filtering.
Search results must resolve to real database entities.

MEAL SIZE
Support planning labels:
micro, light, regular, heavy, very_heavy.
These are planning labels, not medical recommendations.

BUDGET
Eventually support estimated price, cost per serving, cost per gram protein and budget meals.
Keep estimates clearly labelled.

COOKING TIME
Track 5, 10, 20, 30, 60+ minute ranges.
Support quick, office, travel and batch-cooking meals.

AVAILABLE INGREDIENTS
User: "I have eggs, bread, tomato and spinach."
Search available ingredients + templates + diet rules + nutrition targets and return possible meals.

RESTAURANT FOOD
Support restaurant-style recommendations using remaining calories, protein, diet, preferences and meal type.
Scanner should distinguish homemade, restaurant, street food and packaged where possible.

GROCERY ENGINE
Weekly recipes -> ingredients -> normalize quantities -> aggregate -> grocery list.
